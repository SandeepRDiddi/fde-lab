# FDE-014: Scenario generator

**Status:** Done
**Priority:** P1
**Depends on:** FDE-001, FDE-003, FDE-004, FDE-005, FDE-006, FDE-013
**Architecture ref:** architecture.md → AI persona service / Enterprise system mocks / Technical deliverable grading

## User story
As an instructor, I want to paste a raw, messy client requirement and get a
full working scenario out of it — persona, dataset shape, graded technical
task, compliance checklist — instead of hand-authoring every scenario's JSON
config myself.

## Motivation

FDE-013 made the platform grade a real deliverable instead of just prose,
but every scenario's config (persona, dataset domain/messiness, the
technical task and its reference query, the compliance rules) still had to
be hand-written by whoever set the scenario up. That's the other half of
"give requirements, get a full end-to-end FDE Lab scenario": this story
turns a paragraph like "client's nightly CRM sync keeps duplicating orders"
into a complete, immediately-usable scenario config, generated by the same
free local Ollama model persona-service already uses — reviewed by the
instructor, not auto-published sight unseen.

## Acceptance criteria (EARS)
1. WHEN an instructor submits a raw requirement, THE backend SHALL draft a
   scenario config (`persona`, `data_gen`, `technical_task`, and optionally
   `legacy_system`) from it via the local model backend. THE draft SHALL NOT
   include a `compliance_checklist` — a technical-task submission's whole
   content is the SQL query, so a prose rule on that same field could never
   be jointly satisfiable with a working query (found via live testing, see
   the implementation log).
2. THE generated `technical_task.reference_query` SHALL be validated by
   actually executing it against the chosen domain's schema before the
   draft is returned — a hallucinated column or broken query is rejected and
   retried, not handed to the instructor as-is.
3. IF the model's output can't be parsed or repaired after one retry, THEN
   THE backend SHALL return a clear error rather than a broken or
   partially-filled scenario config.
4. WHERE a generated draft is accepted, an instructor SHALL be able to
   review it and create a real scenario instance from it in the same flow,
   without hand-editing JSON.

## Definition of done
- [x] A raw requirement produces a scenario config usable by the existing
      `POST /scenario-instances` unchanged
- [x] A broken model output (bad JSON, unknown domain, non-executing query)
      is caught and retried, not silently accepted

## Implementation log

**2026-09-20** — `backend/app/scenario_generator.py`: `generate_scenario_config`
builds a prompt (`_build_prompt`) that gives the model the two domains
data-gen actually knows how to generate (`ecommerce_orders`,
`hr_employees` — column lists mirrored from
`data-gen/generator/domains.py`, kept in sync by hand since services are
independent per CLAUDE.md) and the two pre-authored legacy-mock scenarios
(`acme-crm`, `northwind-erp` — mirrored from `mocks/legacy-api/scenarios/`,
a closed set since the mock service can't have a new endpoint invented for
it), and asks for one JSON object back (`persona`, `data_gen`,
`technical_task`, `legacy_system`). Calls Ollama's
`/api/chat` directly (`_call_ollama`, same wire contract persona-service's
`gateway.py` uses — duplicated rather than imported, per this repo's
independent-services convention).

`_extract_json` strips markdown code fences if the model adds them and
parses the first `{...}` block. `_validate` then checks the draft:
hard-fails (triggers a retry) on a missing persona field, an unrecognized
`data_gen.domain`, a `reference_query` that isn't a single read-only
`SELECT`, or one that doesn't actually execute against an empty table
shaped like the domain's real columns (`_reference_query_executes` — same
sqlite-based check FDE-013's grader uses, catching a hallucinated column
immediately instead of at first student submission, AC2); soft-defaults
everything else that doesn't affect whether the scenario works (invalid
`messiness` → `"medium"`, malformed compliance rules dropped rather than
failing the whole draft, an unrecognized `legacy_system` value → omitted).
On a hard failure, `generate_scenario_config` retries once with a follow-up
prompt naming the specific problem (small models self-correct reasonably
well from a concrete error message); a second failure raises
`GeneratorError` (AC3), surfaced as a 502 by the new
`POST /scenario-generator/draft` endpoint
(`backend/app/routers/scenario_generator.py`) — not persisted, just
returned for review (AC1, AC4).

Frontend: `ScenarioGenerator` component (new) — a requirement textarea, a
draft preview (persona, domain/messiness, the technical task's instructions
and reference query, compliance rules, legacy system if any), a student-id
field (pre-filled with a random UUID), and "Create & add to cohort", which
`POST`s the (unedited, but instructor-visible) draft straight to the
existing `POST /scenario-instances` — no new creation logic, the generator
just produces input for the endpoint that already existed. Added to
`InstructorConsole` above the scheduling card. Two new Next.js proxy routes
(`/api/scenario-generator/draft`, `/api/scenario-instances`) — the latter
didn't exist yet; every scenario instance before this story was created via
direct `curl` to the backend, a gap noted in `architecture.md`'s open
questions.

Deliberately not automated: data-gen still isn't network-reachable (no HTTP
endpoint, only a CLI invoked via `docker compose run` — a pre-existing gap,
`architecture.md`'s Synthetic data generation section already notes it's
"invoked manually"), so a freshly created instance has no dataset yet. The
created-instance confirmation in the UI prints the exact
`docker compose run --rm data-gen python -m generator <id>` command as the
next manual step, rather than pretending the loop is fully automatic.

Tests (counts below are post-fix, see the live-verification entry that
follows for what the fix was): `backend/tests/test_scenario_generator.py`
(13 tests — valid draft end to end, code-fence stripping, retry-then-succeed
for invalid JSON / unknown domain / hallucinated column / non-`SELECT`
query / dedup-instructions-without-dedup-SQL, hard failure after two
attempts, messiness defaulting, compliance_checklist never emitted even if
the model adds one, unknown legacy system omitted, empty requirement
rejected) and `backend/tests/test_scenario_generator_router.py` (3 tests —
draft endpoint returns a generated config, 502 on persistent generator
failure, and — the actual proof this is useful — a generated draft is
accepted as-is by `POST /scenario-instances` and its `technical_task`
round-trips correctly). All via a monkeypatched `_call_ollama`, same
pattern as FDE-013's fake-S3-client tests. Full backend suite: 88 passed.
Frontend typecheck/build: clean.

Verified live against the real Ollama model (not mocked) — and it caught a
real design bug before this was called done. First live draft (real
requirement: "client's nightly CRM sync keeps duplicating order records")
generated successfully in ~21s and included a `compliance_checklist` with a
rule like "must mention 'data consistency'". Creating an instance from it
and submitting *either* a wrong SQL query *or* the exact reference query
both got rejected — with `"Submission failed the compliance checklist"`.
The platform only has one `content` field per submission; a technical-task
scenario uses it for the SQL query, so a prose `must_include` rule on that
same field can never be satisfied by a working query — the scenario was
unsolvable as generated. Root cause: the prompt asked for a
`compliance_checklist` unconditionally, without accounting for the fact
that a technical-task submission has no separate prose channel for it to
apply to. Fixed by removing `compliance_checklist` entirely from the
generator's output (prompt and `_validate`) — an instructor can still
combine the two by hand-editing a config, but the generator itself never
produces that combination. Re-verified after the fix: same requirement,
fresh instance, real dataset via data-gen, real browser submission — a
non-deduplicating query now correctly shows "Grading failed" and the
correct one "Query graded correct.", with nothing else blocking it.

A second live run surfaced a related, narrower issue: one generated
`reference_query` was syntactically valid and executed fine, but didn't
actually deduplicate anything (`SELECT order_id, customer_name,
customer_email, order_date FROM orders` — no `DISTINCT`/`GROUP BY`) despite
`instructions` describing a duplicate-records problem. Since
`reference_query` *is* the grading ground truth by definition, this
wasn't a crash, but it meant a student who actually followed the written
instructions (added `DISTINCT`) could get marked wrong against a
"reference" that didn't dedupe at all. Added a second heuristic to
`_validate`: if `instructions` mentions duplicates and `reference_query`
contains none of `DISTINCT`/`GROUP BY`/an aggregate, reject and retry
(`_DEDUP_WORDS`/`_DEDUP_SQL`). Strengthened the prompt's schema comment to
say so explicitly too. Re-ran the same requirement several more times
against the real model afterward — 3/3 subsequent attempts produced a
`reference_query` using `DISTINCT` or `GROUP BY` appropriately; one
separate attempt still hit the (unrelated) 2-attempt retry ceiling on a
table-name mismatch the model introduced, surfaced as a clean 502 rather
than a broken scenario, exactly per AC3. This class of residual failure —
occasional retry-exhaustion, or a query that runs but doesn't fully match
its own stated intent in a way this heuristic doesn't happen to catch — is
inherent to a 3B-parameter model and not something to chase further within
this story's scope; an instructor reviewing the draft before creating the
instance (AC4) is the actual backstop, and clicking Generate again after a
502 is cheap.

Both fixes verified live end-to-end afterward via curl and a real browser
(Playwright): generator → instance creation → `data-gen` → student
workspace → correct/incorrect query grading, all against real Ollama
output and a real MinIO-backed dataset, no mocking. Full backend suite
after both fixes: 88 passed (one new test for the dedup heuristic). No
frontend changes were needed for either fix.
